# ADR-0003: Process hosting and the service–UI channel

- **Status:** **Accepted 2026-09-12** (ST-004 merged). Status line updated 2026-09-15. ADR-0007 (proposed 2026-10-27, ST-112) starts an installed service from the machine's Run key rather than the user's, and records what single-file packaging closes of the gaps below.
- **Date:** 2026-09-12
- **Deciders:** project owner; build agent

## Context

Guide §2 and ST-004 describe a per-user background **capture service** and a separate **WPF UI** joined by a named pipe, with per-session tokens, so the UI can crash and restart without losing a recording. Two facts learned in ST-001 shape how that has to be built:

1. **Anything that hooks input or captures the screen must run inside the signed-in user's desktop session.** A Windows Service runs in session 0, which has no interactive desktop: low-level hooks never fire, UI Automation sees nothing, screen captures come back empty. The self-hosted runner had to be set up the same way for the same reason.
2. **Only the technician's own processes should be able to drive capture.** INV-3 and INV-4 assume that a `start`/`stop`/`discard` comes from the ScreenTrail UI the technician can see, not from any process that happens to run as them.

## Decision

### Hosting

- **`ScreenTrail.Service.exe` is a per-user background process, not a Windows Service.** It starts at sign-in from the user's Run key (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, written by the installer in ST-112 and by `LoginStartup` until then) and runs for the whole session with no visible window. Its one window, hidden and untitled, exists so that Windows can ask it to close at sign-out, at shutdown and for an installer's Restart Manager (ST-112, ADR-0007). It owns hooks, capture, redaction, the store and the outbox.
- **`ScreenTrail.UI.exe` runs on demand** (tray, HUD, Review, Settings) or at sign-in, where "Start UI at login" is on by default (amended 2026-11-27, review finding C-I7; the installer's machine Run value starts it, and the user's choice to turn it off is honoured). It holds no capture state; it is a view over the service.
- Exactly one service per user: it takes a named mutex `ScreenTrail.Service.<user-sid>` and exits if it already exists.

### Channel

- **Named pipe `ScreenTrail.<user-sid>`**, server in the service, one instance per connected client. On Windows the pipe ACL admits only the owning user (and no network access). *(Amended 2026-11-28, security fix run, B-01: "no network access" was not true until then, as nothing denied it; the DACL now holds an explicit deny for the NETWORK SID beside the one allow rule, so a connection through the SMB server, which can name any client process id it likes, is refused.)* .NET's pipe API is cross-platform, so the transport and its tests run on the macOS dev box (where it is a Unix socket).
- **A shared PC (amended 2026-11-28, security fix run, B-06).** Pipe names are machine-wide and cannot be reserved without a Windows service, so another account signed in to the same PC can create `ScreenTrail.<user-sid>` before this user's service does. The service then cannot open its pipe (`FirstPipeInstance` refuses it, and the token is never sent to the other pipe, since the UI cannot verify it), no UI reaches the service and nothing is captured until the name is let go. The service keeps trying; it logs the refusal at once and, after five in a row, writes one entry to the Application log (source ScreenTrail, event 1110). A per-install random part of the name and a notice of the service's own in the tray are not done (DEC-20). On a PC shared by several accounts this is a way for one of them to stop another's capture, not to read it.
- **Framing:** 4-byte little-endian length prefix + UTF-8 JSON, one message per frame, 1 MiB maximum. Messages are `type`-discriminated records generated by hand in `ScreenTrail.Shared/Ipc` (System.Text.Json polymorphism, unknown members rejected), the same style as the session schema. Contract version is `IpcContract.Version`.
- **Direction:** commands UI → service (`hello`, answered by `hello_ack`; then `start`, `pause`, `resume`, `stop`, `discard`, `mark_moment`, `get_state`, each answered by a `result`); events service → UI (`hello_ack`, `state_changed`, `rejected`). Every connected, authenticated client receives every event, so a tray, a HUD and a Review window can all be open at once.

### Authentication (per Guide §5, "every command is authenticated with the session token")

A connection must pass three checks before its first command is accepted; failing any one gets a `rejected` reply, an audit row (`ipc_rejected_<reason>`, nothing else), and a closed pipe. *(Amended 2026-11-28, security fix run, B-08: a check that ran past the two-second handshake deadline used to close the pipe with neither. The deadline now covers saying `hello` with the right token, verification has ten seconds of its own and one that runs out gets `rejected` with `slow` and its row; a peer that says nothing in time is sent nothing and gets the row.)*

1. **Same user.** The pipe ACL on Windows; the socket's file permissions elsewhere.
2. **Verified client executable.** The service resolves the client's process from the pipe and checks its executable. Release builds: Authenticode-signed by the same publisher certificate as the service itself. Unsigned (development) builds: the client executable must sit in the same directory as the service executable. *(Amended 2026-11-15: release builds require the same directory as well as the signature, because a signature covers the executable and not the libraries it loads from its folder. The installer puts both executables in one folder under Program Files.)* This is `IClientVerifier`; the Windows implementation lives in the service, tests use fakes. It is what makes ST-004's "unsigned process is rejected" true.
3. **Service-run token.** The service generates a random 32-byte token at start and writes it to `%LOCALAPPDATA%\ScreenTrail\ipc.token` (user-only ACL). The UI reads it and sends it in `hello`; the service compares in constant time. The token rotates every time the service starts, so a stale UI cannot act on a new service run by accident. *(Amended 2026-11-28, security fix run, B-07: the file is written once the service's first pipe instance has claimed the name, before any connection is accepted, rather than before the pipe is made. A copy of the service that cannot claim the name, such as the same account's service in a second Windows session, used to write its token over the running one's, so every UI after that was refused with `bad_token`. The pipe name and the token file are still one per user, not per Windows session (DEC-21).)*

The token does not defend against another process running as the same user reading the file; the executable check does. The token exists so that the *channel* is authenticated per service run and so that a bug that skipped the executable check would still not accept arbitrary connections.

**How far the executable check actually goes (corrected 2026-09-20).** This document used to say it defends against same-user processes, full stop. It does not, and the review of 2026-09-19 said so; what it does is narrower and worth stating exactly.

- It asks the kernel which file the peer was started from, and holds the process open while it checks. It used to read that path out of the peer's own loader data, which a same-user process can rewrite to name our real signed executable, so the check would verify a genuine file on disk while talking to an impostor. *(Amended 2026-11-28, security fix run, B-01: holding the process open does not by itself make it the peer. The id a pipe records is free to name a new process once the one that connected has exited, and the handle is opened after that. Both checks now also read the process's start time from the handle and refuse a process that started after the connection was made (the service from the moment it accepted it, the UI from the moment its connect returned), and the service keeps the handle for the life of the connection, so what it later asks about the connection, such as where its pill is, is asked of the process that passed.)*
- It cannot tell whether a genuine executable is running genuine code. .NET loads another assembly into a signed process when `DOTNET_STARTUP_HOOKS` or the profiler variables ask it to, so an attacker needs no forged binary: launch our real UI with a hook set and it passes for the same reason the real one does. **This is not closed (corrected 2026-10-25).** Both processes refuse to start when those variables are present, unless the build is unsigned, but that check runs at the top of `Main`, after the runtime has already acted on those variables, so it cannot be what keeps their code out. Since 2026-10-25 both projects build with `StartupHookSupport` set to false, so the runtime does not load startup hooks whatever the environment says, and the check at the top of `Main` stays as a second line. Two gaps remain. The builds are framework-dependent, so that switch is carried in the runtime configuration file beside the executable rather than in the executable, and it is only as well protected as the install folder. And the runtime reads the profiler settings before any managed code, so no check in our code can refuse a profiler. Closing both needs a self-contained single-file build with the runtime's diagnostics off, which is packaging, and belongs with ST-112. *(Amended 2026-11-28, security fix run, B-02: the installer's build refuses whether or not it is signed, keyed on a constant `ScreenTrailInstaller=true` compiles in rather than on the signature, and the list also holds the notification-profiler names, `DOTNET_GCPath`, `DOTNET_GCName` and `DOTNET_DiagnosticPorts` under both spellings. The capture service the window starts in that build gets an environment with every `CORECLR_`, `DOTNET_` and `COMPlus_` name removed and `DOTNET_EnableDiagnostics=0`. Said plainly: the refusal cannot see a profiler that hides. The runtime loads it before `Main`, and one that removes its own variables from the process before the check reads them is not caught; the refusal only stops a process started that way from going on as ScreenTrail.)*
- **It still does not cover a DLL planted beside a signed executable.** Only the launcher is signed; the managed assemblies beside it are not, so a copy of our signed `.exe` next to somebody else's `.dll` passes. Closing that needs single-file publishing and signing, which is packaging, and belongs with ST-112. *(Narrowed 2026-11-15: a signed peer must now also run from the verifier's own folder, the install folder under Program Files, so a signed copy in any folder an ordinary user can write to is refused. Both ends read their own path and the peer's from the kernel's record, so they are spelt the same way. Measured on the hosted Windows runner, a process started through a junction or a file symbolic link is recorded under the real file's path, so it is judged by where the file really is. What is left is a library planted in the install folder itself, which takes an administrator, and a file symbolic link to an installed executable placed in another folder, which is judged as the install folder and takes an administrator or Developer Mode to create.)*

The honest summary is that the check raises the cost of impersonation and does not make it impossible, and that the remaining gap is a packaging decision rather than a protocol one.

### Reattach

The service keeps all session state. A client that disconnects for any reason is forgotten; a client that connects gets the current state in `hello_ack`. The UI reconnects with backoff (100 ms, doubling to 2 s) and shows "Capture service not running: Start" (Spec, ST-070) when it can't. A server that fails the UI's verification is asked again every 30 seconds, with the same "not running" meanwhile; nothing is written to it before it is verified, so asking again gives it nothing (amended 2026-11-15; it used to be final until the UI restarted). A handshake the service refuses (`rejected`) is asked again the same way, every 30 seconds, after the quick retries a stale token gets (amended 2026-11-28, security fix run, B-09; it used to be final until the UI restarted). ST-004's requirement is a reattach within 2 s; the transport achieves it in milliseconds.

## Consequences

- The installer (ST-112) registers the Run key for the service and, optionally, the UI. Uninstall removes both.
- The threat model (ST-012) covers: token file confidentiality, the verifier's failure modes, and the pipe ACL. ST-012's service-binary integrity check reuses the same signature logic in the other direction (UI verifying the service), and should replace the verifier's thumbprint comparison with `WinVerifyTrust`, which validates the certificate chain and timestamp as well as the signer.
- ST-020's state machine publishes through the same `state_changed` event; `CaptureStateSnapshot` is deliberately small and grows there.
- What ST-004 leaves to later: pipe ACL hardening beyond the default user-only DACL (ST-012), the UI's connection banner (ST-070), the installer's Run key (ST-112).

## Alternatives considered

- **A real Windows Service plus a per-user helper for capture.** Two more processes and a privilege boundary for no gain: everything that matters must run in the user's session anyway, and the backend holds nothing the service would need elevated rights for.
- **gRPC or HTTP on localhost.** A listening TCP port, which ST-012 forbids in release builds, plus a heavier dependency for a handful of messages.
- **Windows-only pipe code (P/Invoke) instead of `System.IO.Pipes`.** Would move the transport tests to the laptop for no benefit; the ACL and client-process lookup are the only Windows-specific parts and are isolated behind interfaces.
